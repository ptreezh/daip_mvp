# 真实演示系统需求文档

## 项目概述

创建一个真正调用大模型和角色库的演示系统，面向真实用户、真实模型、真实用户故事场景，展示DAIP-LIVE系统的实际能力。

## 需求分析

### 核心问题

当前演示系统存在严重问题：

- 使用模拟数据而非真实LLM调用
- 角色回应是硬编码的假数据
- 没有真正的工作流执行
- 缺乏真实的用户交互体验

### 目标用户

- **技术决策者**: 需要看到真实的技术能力
- **潜在客户**: 需要体验实际的产品功能
- **投资人**: 需要验证技术的可行性
- **开发团队**: 需要测试系统的真实性能

## 功能需求

### 需求1: 真实LLM集成演示

**用户故事**: 作为演示观众，我希望看到系统真正调用大语言模型，而不是预设的假数据。

#### 验收标准

1. WHEN 演示开始 THEN 系统SHALL显示正在连接到真实的LLM服务（如Ollama、OpenAI等）
2. WHEN 用户输入问题 THEN 系统SHALL实时调用LLM并显示真实的响应时间和Token消耗
3. WHEN LLM响应生成 THEN 系统SHALL显示完整的调用过程，包括模型名称、参数设置、输入输出Token数量
4. WHEN 出现LLM错误 THEN 系统SHALL显示真实的错误信息和处理过程

### 需求2: 真实角色库调用演示

**用户故事**: 作为演示观众，我希望看到系统从真实的角色库中加载角色，并展示角色的独特认知特征。

#### 验收标准

1. WHEN 演示启动 THEN 系统SHALL从roles/目录加载真实的角色定义文件
2. WHEN 角色参与讨论 THEN 每个角色SHALL基于其JSON定义文件中的认知框架生成独特回应
3. WHEN 显示角色信息 THEN 系统SHALL展示角色的专业领域、推理风格、价值体系等真实属性
4. WHEN 角色互动 THEN 系统SHALL展示不同角色间的认知差异和观点冲突

### 需求3: 真实工作流执行演示

**用户故事**: 作为演示观众，我希望看到真实的批判性审查和多视角综合工作流的执行过程。

#### 验收标准

1. WHEN 启动批判性审查 THEN 系统SHALL调用真实的CriticalReviewWorkflow类
2. WHEN 执行工作流节点 THEN 系统SHALL显示每个制度原语的真实执行过程和结果
3. WHEN 进行共识计算 THEN 系统SHALL使用真实的共识算法处理角色输入
4. WHEN 检测涌现洞察 THEN 系统SHALL运行真实的EmergentInsightDetector

### 需求4: 真实用户故事场景

**用户故事**: 作为演示观众，我希望看到基于真实业务场景的完整用户故事演示。

#### 验收标准

1. WHEN 选择演示场景 THEN 系统SHALL提供真实的业务场景（如"AI伦理审查"、"产品决策分析"等）
2. WHEN 用户输入观点 THEN 系统SHALL接受真实用户输入而非预设文本
3. WHEN 展示分析结果 THEN 系统SHALL基于真实LLM输出生成分析报告
4. WHEN 保存结果 THEN 系统SHALL将结果真实保存到Wiki系统或文件中

### 需求5: 透明度和可验证性

**用户故事**: 作为技术评估者，我希望能够验证演示的真实性，看到所有技术细节。

#### 验收标准

1. WHEN 演示运行 THEN 系统SHALL实时显示所有LLM调用的详细信息
2. WHEN 处理数据 THEN 系统SHALL显示真实的处理时间、资源消耗、错误处理
3. WHEN 生成结果 THEN 系统SHALL提供结果的可验证性证明（如保存的日志文件）
4. WHEN 演示结束 THEN 系统SHALL生成完整的执行报告，包含所有真实数据

### 需求6: 性能和错误处理演示

**用户故事**: 作为系统评估者，我希望看到系统在真实条件下的性能表现和错误处理能力。

#### 验收标准

1. WHEN LLM服务不可用 THEN 系统SHALL展示真实的错误处理和降级策略
2. WHEN 网络延迟较高 THEN 系统SHALL显示真实的响应时间和用户体验
3. WHEN 处理复杂查询 THEN 系统SHALL展示真实的性能指标和资源使用情况
4. WHEN 并发用户访问 THEN 系统SHALL演示真实的多用户处理能力

### 需求7: 交互式用户体验

**用户故事**: 作为演示参与者，我希望能够真实地与系统交互，而不是观看预录的演示。

#### 验收标准

1. WHEN 我提出问题 THEN 系统SHALL接受我的真实输入并生成个性化回应
2. WHEN 我选择不同角色 THEN 系统SHALL让我与真实的AI角色进行对话
3. WHEN 我修改参数 THEN 系统SHALL根据我的设置调整真实的处理逻辑
4. WHEN 我要求解释 THEN 系统SHALL提供真实的技术解释和演示细节

### 需求8: 自动上下文优化

**用户故事**: 作为系统用户，我希望系统能够自动根据我的历史对话记录、当前任务和可获得的上下文信息，智能优化提供给LLM的上下文，提升对话质量和相关性。

#### 验收标准

1. WHEN 用户发起对话 THEN 系统SHALL自动收集用户历史对话记录、当前任务信息和环境上下文
2. WHEN 系统准备LLM调用 THEN 系统SHALL基于多面嵌入技术（问题模式、目标、解决方案步骤、上下文）自动优化上下文信息
3. WHEN 上下文优化完成 THEN 系统SHALL展示最终优化后的上下文内容，包括相关性评分和选择理由
4. WHEN LLM调用执行 THEN 系统SHALL使用优化后的上下文进行调用，并跟踪优化效果

## 非功能需求

### 性能需求

- 真实LLM调用响应时间 < 30秒
- 角色加载时间 < 5秒
- 工作流执行时间 < 2分钟
- 系统启动时间 < 30秒

### 可靠性需求

- LLM服务连接成功率 > 95%
- 角色库加载成功率 = 100%
- 工作流执行成功率 > 90%
- 错误恢复时间 < 10秒

### 可用性需求

- 演示界面直观易懂
- 技术细节可选择性显示
- 支持中英文双语演示
- 提供详细的操作指南

### 兼容性需求

- 支持多种LLM后端（Ollama、OpenAI、Claude等）
- 兼容现有的角色定义格式
- 集成现有的工作流引擎
- 支持多种输出格式

## 约束条件

### 技术约束

- 必须使用现有的DAIP-LIVE后端架构
- 必须兼容现有的角色库格式
- 必须集成现有的工作流引擎
- 必须支持现有的配置系统

### 业务约束

- 演示时间控制在15-30分钟内
- 支持离线演示（本地LLM）
- 支持在线演示（云端LLM）
- 提供多种复杂度的演示场景

### 安全约束

- 不得泄露敏感的系统配置
- 用户输入必须进行安全过滤
- LLM调用必须有适当的限制
- 演示数据不得包含真实个人信息

## 成功标准

### 技术成功标准

- 所有LLM调用都是真实的，无模拟数据
- 所有角色回应都基于真实的角色定义
- 所有工作流执行都调用真实的后端服务
- 所有演示结果都可以被验证和重现

### 用户体验成功标准

- 观众能够清楚地看到系统的真实能力
- 技术决策者能够验证系统的可行性
- 潜在用户能够理解系统的价值
- 开发团队能够识别系统的问题和改进点

### 业务成功标准

- 演示能够有效展示DAIP-LIVE的核心价值
- 观众对系统的真实性和可靠性有信心
- 演示能够支持商业决策和技术评估
- 系统的技术优势得到充分展现
