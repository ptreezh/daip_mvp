# DAIP-LIVE 项目核心开发原则

本文档记录了在 DAIP-LIVE 项目开发过程中必须遵守的核心原则，以确保代码质量、可维护性和项目目标的稳健达成。

---

### **原则 1: 技术遗产全覆盖原则 (The Legacy Feature Parity Principle)**

**1. 核心思想:**
在对任何旧有代码（尤其是 `src/vendor/old/` 目录下的技术遗产）进行重构或替换时，新的实施计划 **必须** 明确地、完整地覆盖（Account for）旧组件中 **100%** 的功能和责任。

**2. 基本原理:**
旧代码，尽管其架构可能过时，但它是对“已被解决的问题”和“已被实现的需求”的宝贵记录。在没有经过审慎决策的情况下，单方面地“优化”或“忽略”任何既有功能，都可能导致灾难性的功能倒退和对用户承诺的违背。重构的目标是 **改善功能的实现方式**，而不是 **悄无声息地移除功能**。

**3. 与 RIPER-5 协议的集成:**

*   **[MODE: RESEARCH] 阶段:**
    在研究阶段，对旧组件的分析 **必须** 产出一份其所有功能和责任的完整清单。例如，在分析 `lim.py` 时，除了识别出底层的 LLM API 调用，还必须将“历史管理”、“上下文总结”和“RAG 检索”作为三个独立且关键的功能点明确记录下来。

*   **[MODE: PLAN] 阶段:**
    在规划阶段，实施计划和任务清单 **必须** 明确说明每一个被识别出的旧功能将如何被处理。处理方式包括但不限于：
    *   **直接重现 (Direct Re-implementation):** 该功能将在新的组件中被重新构建。
    *   **架构迁移 (Architectural Relocation):** 该功能的职责将被迁移到一个更合适的新组件或现有组件中（例如，将历史管理从 `LLMInterface` 迁移到 `InteractionManager`）。
    *   **主动废弃 (Conscious Deprecation):** 该功能被确认为过时或不再需要，将被移除。**此决策必须在计划中被明确声明、记录并提供理由。**

**4. 必须规避的反模式:**
**永远不要** 假设旧代码中的某个功能不重要或可以被忽略。如果其用途不明确，必须首先寻求澄清。在计划中未明确列出的情况下，任何对既有功能的移除都是对本原则的严重违反。
