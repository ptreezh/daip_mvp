# 详细系统架构设计说明书 (单机版)

## 1. 系统概述

DAIP-LIVE (单机版) 是一个基于多AI角色协作的智能项目执行平台。本系统采用**模块化单体架构**，在单个Python进程中运行，专为单机单用户环境设计。系统优先使用本地部署的大语言模型（LLM），并兼容云端模型作为备选，通过统一的内部模块调用实现所有功能，确保了高性能和易用性。

## 2. 架构设计原则

- **模块化**: 系统功能被划分到不同的Python模块中，各模块职责单一，通过清晰的函数接口进行交互。
- **本地化**: 核心数据（知识库、配置、会话历史）均存储在本地文件系统和SQLite数据库中，无需外部服务依赖。
- **简单性**: 移除了所有网络开销，模块间通信通过直接的函数调用完成，简化了开发、调试和部署。
- **可扩展性**: 通过插件化的“模型提供者”和“工具”设计，可以方便地扩展对新型LLM和外部工具的支持。

## 3. 核心组件详细设计 (内部模块)

### 3.1 角色管理器 (Role Management Module)

- **功能描述**: 负责AI角色的全生命周期管理，是AI行为的核心配置中心。
- **核心功能**:
  - 从指定的本地目录（如 `roles/`）加载角色配置文件（JSON或YAML格式）。
  - 在内存中维护一个角色注册表，缓存已加载的角色对象。
  - 提供`get_role(role_name)`等函数供其他模块调用。
  - 角色的“能力”直接映射到具体的Python函数或工具调用。
- **数据结构**: 角色配置是一个包含名称、描述、个性、Prompt模板和能力列表的Python数据类（dataclass）。
- **交互方式**: 被“个人助理”或“辩论系统”等上层模块直接调用，以获取角色实例和配置。

### 3.2 内存服务 (Memory Service Module)

- **功能描述**: 为AI的思考和会话提供统一的记忆管理，分为短期和长期记忆。
- **核心功能**:
  - **短期记忆**: 在一个会话的生命周期内，将会话历史、中间思考过程等存储在内存中的一个Python对象里。
  - **长期记忆**: 在会话结束或关键节点，通过调用`Persistence Layer`将重要信息（如会话摘要、关键决策）持久化到SQLite数据库中。
  - **记忆检索**: 提供`retrieve_memory(query)`等函数，用于从历史会话中检索相关信息。
- **交互方式**: 与“知识管理器”紧密协作，将检索到的知识和记忆片段一同组合，为“模型提供者”生成最终的上下文（Context）。

### 3.3 知识管理器 (Knowledge Management Module)

- **功能描述**: 负责本地知识的摄取、向量化、存储和检索。
- **核心功能**:
  - **知识摄取**: 监视指定的本地知识文件夹，自动处理新增或修改的文档（.md, .txt, .pdf等）。
  - **向量化**: 调用“模型提供者”中的嵌入模型（Embedding Model），将文本块转换为向量。
  - **存储与索引**: 将文本块和对应的向量存储在本地的嵌入式向量数据库（如FAISS索引文件, ChromaDB数据库文件）中。
  - **语义搜索**: 提供`search_knowledge(query_text, top_k)`函数，根据文本相似度返回最相关的知识片段。
- **交互方式**: 被“内存服务”调用，为生成LLM上下文提供外部知识支持。

### 3.4 辩论服务 (Debate Service Module)

- **功能描述**: 组织和管理一场结构化的多角色辩论流程。
- **核心功能**:
  - **流程控制**: 根据预设规则（如发言顺序、辩论轮次）依次调用不同的AI角色。
  - **观点记录**: 将每个角色的发言、论点、反驳记录在会话的短期记忆中。
  - **共识评估**: 在辩论结束后，调用LLM对整个辩论过程进行分析，生成摘要和共识评估报告。
- **交互方式**: 作为一个高级业务流程，调用“角色管理器”获取角色，调用“内存服务”记录历史，并通过“模型提供者”让角色“发言”。

### 3.5 工作流引擎 (Workflow Engine Module)

- **功能描述**: 编排和执行由一系列任务（Task）组成的复杂业务流程。
- **核心功能**:
  - **工作流定义**: 从本地YAML或JSON文件加载工作流定义，包括任务列表、依赖关系和参数。
  - **任务执行**: 按照依赖关系图（DAG）顺序执行任务。每个任务可以是一个Python函数调用、一次LLM调用或一个外部工具调用。
  - **状态跟踪**: 将执行状态和结果实时记录到SQLite数据库中。
- **交互方式**: 由用户通过CLI或Web UI启动，是实现自动化的核心模块。

### 3.6 模型提供者 (Model Provider Module)

- **功能描述**: **系统的关键抽象层**，封装了与不同LLM交互的复杂性，为上层模块提供统一、简单的调用接口。
- **核心功能**:
  - **统一接口**: 定义通用的`generate(prompt, params)`和`embed(text)`接口。
  - **本地模型支持**: 实现一个或多个“本地提供者”，例如：
    - `OllamaProvider`: 通过HTTP请求与本地运行的Ollama服务通信。
    - `LlamaCppProvider`: 通过Python绑定直接调用llama.cpp库加载GGUF等格式的模型文件。
  - **云端模型支持**: 实现多个“云端提供者”，例如：
    - `OpenAIProvider`: 调用OpenAI的API。
    - `GeminiProvider`: 调用Google的Gemini API。
  - **模型切换**: 用户可以在总配置文件中简单地切换`provider: ollama`或`provider: openai`，即可改变整个系统使用的LLM，无需修改任何代码。
- **交互方式**: 作为底层服务，被所有需要LLM能力的模块（如辩论服务、个人助理）调用。

## 4. 数据流与模块交互

以一次“个人助理”的问答为例：

1.  **用户输入**: 用户通过CLI或Web UI提问：“根据我知识库里的内容，总结一下项目A的风险。”
2.  **个人助理**: 接收到问题，将其分解为两个子任务：(a) 检索“项目A风险”的知识；(b) 进行总结。
3.  **知识检索**: “个人助理”调用“内存服务”，后者再调用“知识管理器”的`search_knowledge`函数。 
4.  **知识管理器**: 将问题文本“项目A的风险”向量化，在本地FAISS/ChromaDB索引中进行相似度搜索，返回最相关的几个知识片段。
5.  **上下文生成**: “内存服务”将检索到的知识片段与会话历史组合成一个丰富的上下文（Context）。
6.  **LLM调用**: “个人助理”将组合好的上下文和“请总结风险”的指令，一起传递给“模型提供者”的`generate`函数。
7.  **模型提供者**: 根据当前配置（例如`provider: ollama`），选择`OllamaProvider`，向本地Ollama服务发送请求。
8.  **结果返回**: 本地LLM生成总结，结果通过`OllamaProvider` -> `个人助理` -> `交互层`，最终呈现给用户。

## 5. 数据持久化设计

- **SQLite数据库 (`daip_live.db`)**: 单个文件，存储所有结构化数据。
  - `roles`表: 存储角色配置。
  - `sessions`表: 存储会话的元数据和长期记忆摘要。
  - `workflows`表: 存储工作流定义和执行历史。
  - `knowledge_metadata`表: 存储知识条目的元数据（如文件路径、标题等）。
- **本地文件系统**:
  - `config.yaml`: 存储系统的主配置，如使用的模型提供者、API Keys等。
  - `knowledge/`: 存放用户提供的原始知识文档。
  - `vector_store/`: 存放由知识管理器生成的向量索引文件（如FAISS的`.index`文件或ChromaDB的数据库目录）。
  - `logs/`: 存放系统运行日志。
