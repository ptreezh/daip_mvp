# iFlow 项目配置文档

## 项目概述

DAIP-LIVE (Dynamic AI-driven Project-execution LIVE system) 是一个运行在本地个人电脑上的智能协作与执行平台。它通过多AI角色协作、结构化辩论和本地知识库管理，为单个用户提供强大的决策和分析支持。

本系统**以本地大语言模型为核心，云端模型为辅助**，所有核心功能均可在离线环境下运行，确保了用户的隐私和数据安全。

## 系统架构

DAIP-LIVE (单机版) 采用**模块化单体应用架构**。整个系统作为一个独立的本地Python进程运行，其核心是一个**动态的、分层的Agent执行引擎**，而非一个静态的工作流系统。此架构支持用户通过**异步消息队列**对AI的思考和执行过程进行**实时驾驭 (Real-time Steering)**，代表了下一代AI助手的交互模式。

### 核心设计原则

- **动态与自适应**: AI的行为由其自身的**规划（Todo系统）**和对环境的感知驱动，而非完全依赖预设的静态流程。
- **实时交互**: 用户是"驾驶员"，而非"乘客"。用户可以在AI执行任务的任何时刻进行干预、提问和修正。
- **隔离与并发**: 通过**子Agent (SubAgent)** 机制，将复杂任务分解给隔离的、并行的执行单元，提升效率和稳定性。
- **安全与可控**: 通过**多层权限**和**前置条件检查**，确保AI工具的使用既强大又安全。

## 核心模块说明

### 交互层 (Interface Layer)
- **CLI/TUI/GUI**: 用户的操作入口。
- **异步消息队列 (Async Message Queue)**: 这是实现实时驾驭的关键。用户的任何输入都会被立即放入此队列。主Agent执行引擎在循环的每个关键节点都会检查此队列，以获取用户的最新指令，从而实现动态调整。

### 核心逻辑层 (Core Logic Layer)
- **主Agent执行引擎**: 取代了旧的"工作流引擎"。它不是执行一个固定的流程，而是围绕一个**"思考-行动"循环**来工作，其行为由一个内置的`Todo`列表（任务规划）来指导。它可以调用其他逻辑模块或服务层的工具。
- **子Agent派生能力**: 引擎中的`Task`工具可以根据需要，实例化一个或多个隔离的**子Agent**来并行处理复杂任务。
- **辩论系统 / 角色管理器**: 作为被主Agent引擎调用的高级逻辑模块。

### 核心服务层 (Core Service Layer)
- **数据持久化服务 (P1)**: 负责管理结构化数据的生命周期，包括数据库的初始化、表的创建，以及对核心对象的增、删、改、查操作。
- **知识管理服务 (P2)**: 负责实现完整的RAG（检索增强生成）流程中的"检索"部分，将非结构化文档转化为可检索的知识。
- **模型提供者服务 (P3)**: 作为系统与大语言模型的桥梁，通过工厂模式和统一接口实现对不同LLM后端的可插拔支持。
- **角色与工具核心 (P4)**: 作为AI"大脑"与"手"的关键枢纽，负责解析AI角色定义并提供安全的工具调用框架。
- **统一人类助手 (P8)**: 作为系统的智能协调中心，负责端到端的多角色工作流编排、用户记忆管理、提示词优化和Token优化。

## 技术栈

- **语言**: Python >=3.9, <3.12
- **包管理**: Poetry
- **CLI框架**: Typer
- **TUI框架**: Textual
- **GUI框架**: Streamlit
- **数据验证**: Pydantic
- **数据持久化**: SQLite
- **知识管理**: FAISS, Langchain
- **开发工具**: pytest, mypy, ruff, pre-commit

## 开发实践

- 使用 Poetry 进行依赖管理
- 使用 ruff 进行代码格式化和 linting
- 使用 mypy 进行类型检查
- 使用 pytest 进行测试
- 使用 pre-commit 钩子确保代码质量

## CLI 命令结构

应提供一个统一的入口命令（如`daip`），并包含以下子命令：

- **`daip project scaffold [--description <text> | --from-file <path>]`**: 调用"AI生成SOP"功能。
- **`daip agent run "<goal>"`**: 直接启动Agent，执行一个高阶目标。
- **`daip knowledge sync`**: 手动同步知识库。
- **`daip knowledge search "<query>"`**: 搜索知识库内容。
- **`daip config view` / `daip config set <key> <value>`**: 查看和设置配置。
- **`daip session list`**: 列出历史会话。

## TUI 核心交互界面 ("Gemini模式")

当用户运行`daip agent run`等交互式命令时，系统应启动一个全屏的TUI应用。此界面必须严格实现我们在《需求规格说明书》4.6.2节中定义的**所有"Gemini模式"交互需求**。

**界面布局:**
- **主聊天窗口**: 一个可滚动的区域，用于展示对话历史。
- **状态栏 (Status Bar)**: 位于屏幕底部或顶部，**必须**实时显示：
  - **当前模型**: e.g., `llama3:8b`
  - **上下文使用率**: e.g., `Tokens: 4100/8192 (50%)`，并根据使用率改变颜色。
  - **系统状态**: e.g., `[正在思考...]`, `[正在调用工具: read_file]`。
- **输入框**: 位于底部，用于用户输入。**必须支持**在Agent工作时，用户依然可以输入和提交新指令（实现异步消息队列）。

**内容渲染要求:**
1.  **Agent思考/计划**: 必须以一种特殊的样式（如斜体、特定颜色）展示。
2.  **工具调用**: 必须在一个带边框、高亮的区块中展示，包含工具名和参数。
3.  **工具输出**: 必须在一个带边框、有成功/失败标识的区块中展示。代码和JSON必须有**语法高亮**。长内容必须**可滚动**。
4.  **LLM回复**: 必须以**流式"打字机"**效果逐字显示。
5.  **Markdown渲染**: LLM的回复必须能正确渲染列表、粗体、斜体和代码块。

## 其他TUI功能

- **权限请求弹窗**: 当工具权限为`ask`时，必须弹出一个模态对话框，要求用户按"Y"或"N"进行确认。
- **可访问性**: 应支持基本的键盘导航（如`Tab`切换焦点，`↑/↓`滚动）。

## GUI 核心交互界面 ("Gemini模式")

GUI界面同样需要严格遵循"Gemini模式"的交互需求：

**页面布局:**
- **主会话页面**: 核心的对话和任务执行界面，包含可滚动的对话历史记录区域。
- **知识库管理页面**: 用于管理本地知识源，显示已索引文件的列表、状态和统计信息。
- **设置页面**: 用于配置系统和管理密钥，包括模型提供者切换、API密钥管理、工具权限管理等。

**信息展示要求:**
1.  **显式的意图与规划**: 在执行任何复杂操作或调用工具前，系统应首先清晰地展示其"思考"或"计划"。
2.  **透明的工具调用**: 当系统使用工具时，必须在界面上以一个独立的、高亮的区块展示完整的工具调用信息。
3.  **明确的工具输出**: 工具执行后的返回结果，必须在一个独立的、结构化的区块中展示，使用颜色或图标明确标识成功/失败状态。
4.  **流式响应**: 所有来自LLM的最终文字回答，都必须以流式"打字机"效果逐字显示。
5.  **Markdown渲染**: 界面必须能正确解析并渲染LLM回答中的Markdown语法。

## 国际化支持

- **字符串外部化**: 所有面向用户的字符串都不能硬编码在代码中，必须使用标准的i18n框架进行管理。
- **语言资源文件**: 支持中文（`zh_CN`）和英文（`en`）两种语言，语言资源文件存放在指定的`locales/`目录中。
- **语言切换**: 系统应能自动检测操作系统的语言设置，并将其作为默认语言，用户也能在设置界面或通过`config.yaml`文件手动切换语言。
