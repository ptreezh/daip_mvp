# P5-P7 模块重构需求规格说明书

## 文档信息

- **文档版本**: v1.0

## 1. 引言

### 1.1 目的
本文档基于现有的DAIP-LIVE系统规格文档，为P5 Agent Engine、P6 TUI和P7 GUI模块的重构提供详细的需求规格说明。重构的目标是在不影响现有系统使用的前提下，通过隔离备份的方式，实现模块的现代化改造。

### 1.2 范围
本重构计划涵盖以下三个核心模块：
- **P5 Agent Engine**: 解耦重构，降低复杂度
- **P6 TUI**: UI组件模块化
- **P7 GUI**: 补充完整实现

### 1.3 重构原则
1. **隔离原则**: 重构过程不影响现有系统的正常使用
2. **备份原则**: 原有模块必须完整备份，支持快速回滚
3. **渐进原则**: 采用分阶段实施，每个阶段都可独立交付和验证
4. **兼容原则**: 新实现必须保持与现有接口的兼容性
5. **测试原则**: 每个阶段都必须有完整的测试验证

## 2. P5 Agent Engine 重构需求

### 2.1 现状分析
基于现有规格文档分析：

#### 2.1.1 当前架构问题
- **复杂度评分**: 984 (高复杂度)
- **文件数量**: 14个Python文件
- **大文件问题**: 5个文件超过300行，最大文件562行
- **依赖复杂**: 6个直接依赖，存在循环依赖风险

#### 2.1.2 功能需求合规性
根据P5 Agent Engine规格文档，必须保持以下功能：
- ✅ `get_status()` API (AgentStatus模型)
- ✅ 任务导向模式 (`run`方法)
- ✅ 对话模式 (`chat_run`方法)
- ✅ 状态管理 (AgentState枚举)
- ✅ Token使用统计
- ✅ 模型名称管理

### 2.2 重构需求规格

#### 2.2.1 架构解耦需求

**需求ID**: P5-ARCH-001
**优先级**: 高
**描述**: 将单体AgentEngine拆分为松耦合的微服务架构

**具体要求**:
1. **事件总线系统**
   - 实现EventBus类，支持事件发布/订阅
   - 支持异步事件流处理
   - 事件类型定义和类型安全

2. **领域服务拆分**
   - IntentRecognitionService: 意图识别服务
   - ExecutionEngineService: 执行引擎服务
   - StateManagementService: 状态管理服务
   - PermissionService: 权限控制服务

3. **依赖注入容器**
   - ServiceContainer类管理服务生命周期
   - 支持Singleton、Transient等作用域
   - 配置化的服务注册和解析

#### 2.2.2 接口兼容需求

**需求ID**: P5-COMPAT-001
**优先级**: 高
**描述**: 确保重构后的模块与现有系统完全兼容

**具体要求**:
1. **AgentStatus API兼容性**
   ```python
   # 必须保持现有接口
   def get_status() -> AgentStatus:
       """保持现有的返回类型和数据结构"""
   ```

2. **执行模式兼容性**
   ```python
   # 必须保持现有方法签名
   async def run(self, goal: str, ...) -> AsyncGenerator[AgentEvent, None]:
   async def chat_run(self, initial_goal: str) -> AsyncGenerator[AgentEvent, None]:
   ```

3. **状态管理兼容性**
   - 保持AgentState枚举定义
   - 保持状态转换逻辑
   - 保持状态持久化格式

#### 2.2.3 性能需求

**需求ID**: P5-PERF-001
**优先级**: 中
**描述**: 重构后性能不得低于现有实现

**具体要求**:
1. **响应时间**: 命令响应时间 ≤ 当前实现
2. **内存使用**: 内存占用 ≤ 当前实现的120%
3. **并发能力**: 支持现有并发度
4. **启动时间**: 冷启动时间 ≤ 5秒

#### 2.2.4 测试需求

**需求ID**: P5-TEST-001
**优先级**: 高
**描述**: 新架构必须支持完整的单元测试和集成测试

**具体要求**:
1. **单元测试覆盖率**: ≥ 90%
2. **集成测试**: 覆盖所有主要执行路径
3. **性能测试**: 基准测试和回归测试
4. **兼容性测试**: 与现有系统的接口兼容性验证

## 3. P6 TUI 组件化重构需求

### 3.1 现状分析

#### 3.1.1 当前架构问题
- **代码集中**: 2877行代码集中在tui.py文件
- **组件缺失**: 缺乏可复用的UI组件
- **维护困难**: 修改影响面大，风险高
- **扩展性差**: 添加新功能需要修改核心文件

#### 3.1.2 TUI组件规格合规性
根据TUI组件规格文档，必须保持以下组件规范：
- ✅ 组件标识符规范 (主界面组件ID)
- ✅ 组件访问规范 (查询方法)
- ✅ 消息格式规范 (颜色标签)
- ✅ 测试兼容性规范 (Mock对象兼容性)

### 3.2 重构需求规格

#### 3.2.1 组件架构需求

**需求ID**: P6-ARCH-001
**优先级**: 高
**描述**: 将单体TUI拆分为可复用的组件库

**具体要求**:
1. **组件基类设计**
   ```python
   class TUIComponent(ABC):
       @abstractmethod
       def render(self) -> Widget:
           pass

       async def mount(self) -> None:
           pass

       def update_state(self, **kwargs) -> None:
           pass
   ```

2. **核心组件实现**
   - LayoutComponent: 主布局组件
   - NavigationComponent: 导航组件
   - ContentComponent: 内容区域组件
   - InputAreaComponent: 输入区域组件
   - DisplayAreaComponent: 显示区域组件
   - StatusBarComponent: 状态栏组件

3. **组件通信机制**
   - 事件驱动的组件间通信
   - 状态管理器统一管理状态
   - 组件生命周期管理

#### 3.2.2 组件兼容性需求

**需求ID**: P6-COMPAT-001
**优先级**: 高
**描述**: 确保组件化后的TUI与现有组件规范完全兼容

**具体要求**:
1. **组件ID兼容性**
   ```python
   # 必须保持现有组件ID
   #main_log, #user_input, #status_bar, #header, #footer
   #dialog, #permission-label, #allow, #deny
   ```

2. **查询方法兼容性**
   ```python
   # 必须保持现有查询方式
   log_view = self.query_one("#main_log", RichLog)
   user_input = self.query_one("#user_input", Input)
   ```

3. **更新方法兼容性**
   ```python
   # 必须保持现有更新方式
   log_view.write("新的文本内容")
   status_bar.update("新的状态信息")
   ```

#### 3.2.3 状态管理需求

**需求ID**: P6-STATE-001
**优先级**: 中
**描述**: 实现统一的TUI状态管理系统

**具体要求**:
1. **状态管理器**
   ```python

       def update_state(self, updates: Dict[str, Any]) -> None:
       def subscribe(self, key: str, callback: Callable) -> None:
   ```

2. **响应式更新**
   - 状态变更自动触发UI更新
   - 支持状态变更监听
   - 批量状态更新优化

#### 3.2.4 主题系统需求

**需求ID**: P6-THEME-001
**优先级**: 低
**描述**: 实现可配置的主题系统

**具体要求**:

2. **样式一致性**
   - 统一的样式规范
   - 可扩展的样式系统

## 4. P7 GUI 完整实现需求

- **用户体验**: 与现代化GUI存在差距

#### 4.1.2 技术栈选择需求
基于现代化要求，需要选择合适的技术栈：
- **GUI框架**: CustomTkinter (现代化Tkinter)
- **架构模式**: MVVM (Model-View-ViewModel)
- **状态管理**: 响应式数据绑定
- **主题系统**: 深色/浅色主题

### 4.2 实现需求规格

#### 4.2.1 MVVM架构需求

**需求ID**: P7-ARCH-001
**优先级**: 高
**描述**: 实现完整的MVVM架构模式

**具体要求**:
1. **ViewModel基类**
   ```python
   class ViewModel(ABC):
       def set_property(self, name: str, value: Any) -> None:
       def register_command(self, name: str, command: Command) -> None:
       def execute_command(self, name: str, *args, **kwargs) -> Any:
   ```

2. **命令模式**
   ```python
   class Command:
       def __init__(self, execute_func: Callable, can_execute_func: Callable = None):
       def execute(self, *args, **kwargs) -> Any:
       def can_execute(self) -> bool:
   ```

3. **数据绑定机制**
   - 属性变更自动通知
   - 单向/双向数据绑定
   - 批量更新优化

#### 4.2.2 功能对等需求

**需求ID**: P7-FEAT-001
**优先级**: 高
**描述**: GUI功能必须与TUI功能完全对等

**具体要求**:

2. **用户体验对等**
   - 操作流程一致
   - 信息展示一致
   - 错误处理一致
   - 快捷键支持

3. **性能对等**
   - 响应速度相当
   - 内存使用合理
   - 启动时间可接受

#### 4.2.3 共享业务逻辑需求

**需求ID**: P7-SHARED-001
**优先级**: 高
**描述**: GUI和TUI必须共享相同的业务逻辑层

**具体要求**:
1. **抽象接口层**
   ```python
   class InteractionLayer(ABC):
       @abstractmethod
       async def send_message(self, message: str) -> AsyncGenerator[MessageEvent, None]:
       @abstractmethod
   ```

2. **实现层**
   - TUIInteractionLayer: TUI专用实现
   - GUIInteractionLayer: GUI专用实现
   - 共享核心业务逻辑

#### 4.2.4 跨平台兼容需求

**需求ID**: P7-PLATFORM-001
**优先级**: 中
**描述**: GUI必须支持主流操作系统

## 5. 隔离备份策略需求

### 5.1 隔离原则

**需求ID**: ISO-ISO-001
**优先级**: 高
**描述**: 重构过程必须完全隔离，不影响现有系统

**具体要求**:
1. **版本隔离**
   - 重构版本在独立的目录结构中
   - 保持原有版本完全不变
   - 支持版本间的独立运行

2. **配置隔离**
   - 重构版本使用独立的配置文件
   - 支持配置迁移和对比
   - 原有配置保持不变

3. **数据隔离**
   - 数据存储使用独立的数据库文件
   - 支持数据迁移和同步
   - 原有数据完全保留

### 5.2 备份策略

**需求ID**: ISO-BACKUP-001
**优先级**: 高
**描述**: 必须提供完整的备份和回滚机制

**具体要求**:
1. **自动备份**
   - 重构前自动备份原有模块
   - 备份包含所有必要文件
   - 备份文件包含版本信息

2. **版本管理**
   - 支持多版本备份管理
   - 支持版本对比和差异分析
   - 支持选择性版本恢复

3. **快速回滚**
   - 支持一键回滚到原有版本
   - 回滚过程自动化
   - 回滚后系统立即可用

### 5.3 并行运行需求

**需求ID**: ISO-PARALLEL-001
**优先级**: 中
**描述**: 支持新旧版本的并行运行和对比

**具体要求**:
1. **并行部署**
   - 支持新旧版本同时部署
   - 支持端口配置避免冲突
   - 支持独立的数据目录

2. **功能对比**
   - 支持相同输入的并行测试
   - 支持输出结果的对比分析
   - 支持性能指标的对比
