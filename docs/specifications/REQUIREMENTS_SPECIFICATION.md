# 需求规格说明书

## 1. 引言

### 1.1 目的
本文档旨在定义DAIP-LIVE系统的完整需求规格，为系统设计、开发、测试和部署提供明确的指导和依据。通过详细描述系统的功能需求、非功能需求和约束条件，确保开发团队和利益相关者对系统需求有一致的理解。

### 1.2 范围
DAIP-LIVE (Dynamic AI-driven Project-execution LIVE system) 是一个智能协作平台，支持多AI角色协作与知识管理。系统通过动态AI驱动实现实时项目执行和知识管理，主要面向需要复杂决策支持和知识协作的组织和团队。

## 2. 项目概述

### 2.1 产品描述
DAIP-LIVE是一个基于多AI角色协作的智能项目执行平台，通过动态AI驱动实现实时项目执行和知识管理。系统利用AI提示词和MCP协议，让开发更智能、更高效。

### 2.2 产品功能
- 多AI角色协作：支持多个AI角色协同工作
- 智能辩论系统：结构化辩论与共识形成
- 知识管理：基于向量数据库的智能检索
- 个人助理：统一入口处理复杂任务
- Wiki协作：知识沉淀与团队协作

### 2.3 用户特征
由于本系统是单机单用户应用，系统的使用者被统一视为“用户”。用户是系统的操作者，负责配置系统、管理知识、发起任务和使用系统产出的结果。

### 2.4 运行环境
- **本地环境**: 系统作为一个独立的应用程序，在用户的个人电脑（Windows, macOS, Linux）上直接运行。
- **网络环境**: 核心功能支持完全离线运行。仅在使用云端LLM服务时，需要互联网连接。

## 3. 功能需求

### 3.1 系统配置模块

**功能描述**: 用户可以通过配置文件或图形界面管理应用的全局设置。系统支持分层配置，允许项目级配置覆盖全局配置。

**参与者**: 用户、系统

#### 3.1.1 分层配置文件管理
- **全局配置**: 系统根目录下有一个全局的`config.yaml`文件，用于定义用户的通用设置。
- **项目级配置**: 用户可以在其任何一个工作目录（项目文件夹）下，创建一个`.daip/config.yaml`文件。当应用在此目录下运行时，项目级配置中的同名设置，将会**覆盖**全局配置。
- **加载优先级**: 系统在读取配置时，必须遵循明确的优先级链条：**环境变量 > 项目级配置 > 全局配置**。即，如果一个设置在环境变量和配置文件中都存在，以环境变量为准。这为临时修改配置或在脚本中运行提供了最大的灵活性。

#### 3.1.2 API密钥管理
**功能描述**: 为方便使用云端LLM服务，用户需要在系统中配置API密钥。
**基本流程**:
1. 用户在Web UI的设置页面找到“API密钥管理”部分。
2. 用户为需要使用的云端服务（如OpenAI, Gemini）输入API Key。
3. 系统将加密后的密钥安全地存储在本地（例如使用操作系统的密钥链或一个本地加密文件），而不是明文存储在配置文件中。
4. 当调用云端模型时，系统自动加载并使用对应的密钥。

### 3.2 角色管理模块

#### 3.2.1 角色定义
**功能描述**：系统支持创建和配置AI角色。
**参与者**：用户
**前置条件**：系统正常运行。
**后置条件**：新角色被成功创建并可用。
**基本流程**：
1. 用户访问角色管理界面。
2. 用户选择创建新角色。
3. 用户填写角色基本信息(名称、描述等)。
4. 用户配置角色能力和服务。
5. 用户定义角色个性特征。
6. 用户保存角色配置。
7. 系统验证配置并创建角色。

**输入约束**：
- 角色名称：1-100字符，唯一性。
- 描述信息：0-500字符。
- 能力列表：至少包含一项能力。

#### 3.2.2 角色配置
**功能描述**：用户可以修改现有角色的配置。
**参与者**：用户
**前置条件**：目标角色已存在。
**后置条件**：角色配置被成功更新。
**基本流程**：
1. 用户选择要修改的角色。
2. 用户修改角色配置参数。
3. 用户保存更改。
4. 系统验证配置有效性。
5. 系统更新角色配置。

#### 3.2.3 角色状态管理
**功能描述**：系统支持启用、禁用和删除角色。
**参与者**：用户
**前置条件**：角色已存在。
**后置条件**：角色状态被正确更新或角色被删除。
**基本流程**：
1. 用户选择目标角色。
2. 用户执行状态变更操作(启用/禁用/删除)。
3. 系统验证操作可行性（例如，角色是否正在被激活的会话使用）。
4. 系统更新角色状态或删除角色。
5. 系统记录操作日志。

### 3.3 会话管理模块

#### 3.3.1 会话创建
**功能描述**：用户可以创建新的协作会话。
**参与者**：用户
**前置条件**：系统正常运行。
**后置条件**：新会话被成功创建。
**基本流程**：
1. 用户选择创建会话。
2. 用户填写会话信息(标题、描述、类型)。
3. 用户选择参与角色。
4. 用户确认创建。
5. 系统验证信息并创建会话。
6. 用户进入会话界面。

**输入约束**：
- 会话标题：1-200字符。
- 参与角色：至少选择一个角色。
- 会话类型：聊天、辩论或工作流。

#### 3.3.2 会话参与
**功能描述**：用户和AI角色可以参与会话交互。
**参与者**：用户、AI角色
**前置条件**：会话已创建且处于活跃状态。
**后置条件**：消息被成功发送和接收。
**基本流程**：
1. 用户或AI角色在会话中生成内容。
2. 系统接收并处理消息。
3. 系统将消息追加到会话历史中并更新界面。

#### 3.3.3 会话控制
**功能描述**：用户可以控制会话的进行状态。
**参与者**：用户
**前置条件**：会话已创建。
**后置条件**：会话状态被正确更新。
**基本流程**：
1. 用户选择会话控制操作(暂停、恢复、结束)。
2. 系统执行状态变更。
3. 系统通知所有参与方（主要是AI角色）状态变更。
4. 系统记录操作日志。

### 3.4 知识管理模块

#### 3.4.1 知识录入
**功能描述**：用户可以将本地的文档或手动输入的条目添加为知识。
**参与者**：用户
**前置条件**：系统正常运行。
**后置条件**：新知识条目被成功处理并索引。
**基本流程**：
1. 用户指定一个本地文件夹作为知识库源。
2. 系统自动检测文件变更，或用户手动触发同步。
3. 系统处理文件内容，生成向量表示并存入本地向量数据库。

**输入约束**：
- 支持的文件格式：Markdown, TXT, PDF等。

#### 3.4.2 知识检索
**功能描述**：用户可以通过关键字或自然语言问题搜索相关知识。
**参与者**：用户
**前置条件**：知识库中存在已索引的知识。
**后置条件**：返回相关的知识条目列表。
**基本流程**：
1. 用户在CLI或Web UI中输入搜索请求。
2. 系统根据请求在向量数据库中进行语义搜索。
3. 系统按相关性排序结果。
4. 系统返回搜索结果。

#### 3.4.3 知识更新
**功能描述**：用户可以通过修改源文件来更新知识。
**参与者**：用户
**前置条件**：知识文件已存在。
**后置条件**：更新后的知识被重新索引。
**基本流程**：
1. 用户在本地文件系统直接编辑知识文件。
2. 用户触发知识库同步。
3. 系统检测到文件哈希值变更，重新对该文件进行处理和索引。

### 3.5 辩论系统模块

#### 3.5.1 辩论发起
**功能描述**：用户可以发起新的辩论会话。
**参与者**：用户
**前置条件**：系统正常运行。
**后置条件**：辩论会话被成功创建。
**基本流程**：
1. 用户选择发起辩论。
2. 用户填写辩论主题。
3. 用户选择参与角色。
4. 用户设置辩论参数(轮数、时间等)。
5. 用户确认发起辩论。
6. 系统创建辩论会话。

#### 3.5.2 辩论进行
**功能描述**：AI角色按照设定规则进行辩论。
**参与者**：AI角色、系统
**前置条件**：辩论会话已创建且处于进行中状态。
**后置条件**：辩论按流程进行，观点被记录。
**基本流程**：
1. 系统确定当前发言角色。
2. 角色生成发言内容。
3. 系统接收并记录发言。
4. 系统分析发言内容。
5. 系统更新辩论状态。
6. 系统确定下一个发言角色。
7. 重复上述流程直至辩论结束。

#### 3.5.3 共识形成
**功能描述**：系统根据辩论内容形成共识结论。
**参与者**：系统
**前置条件**：辩论会话已结束。
**后置条件**：生成共识结论报告。
**基本流程**：
1. 系统收集所有辩论观点。
2. 系统分析观点相似性和一致性。
3. 系统计算共识度评分。
4. 系统识别主要共识点。
5. 系统生成共识结论报告。
6. 系统存储共识结果。

### 3.6 Agent执行引擎模块 (v3.0)

**功能描述**: 此模块是系统的核心，取代了传统的静态工作流引擎。它使系统具备动态规划和分层执行复杂任务的能力。

#### 3.6.1 `Todo`清单与自主规划
- **功能描述**: Agent在接收到高阶任务后，首要行动是自我规划，生成一个对用户可见的、有序的`Todo`任务清单。
- **基本流程**:
  1. Agent调用内置的`TodoWrite`工具，创建初步的任务项。
  2. 在执行过程中，Agent持续调用`TodoWrite`更新任务状态（如从未开始->进行中->已完成），或根据新发现动态添加、修改任务项。
  3. `Todo`清单应在UI/TUI中清晰展示，作为Agent的“工作计划板”。

#### 3.6.2 `Task`工具与子Agent派生
- **功能描述**: 对于`Todo`清单中的复杂任务，主Agent可以通过调用`Task`工具，派生一个或多个并行的、隔离的子Agent来完成。
- **基本流程**:
  1. 主Agent决定将一个复杂任务（如“分析X文件”）进行委派。
  2. 主Agent调用`Task`工具，并传入该任务的详细指令。
  3. 系统为这个`Task`实例化一个全新的子Agent，该Agent拥有独立的、更精简的上下文和工具集。
  4. 子Agent独立完成任务，并将结果返回给主Agent。
  5. 主Agent根据返回结果，更新`Todo`清单中的对应任务项状态。

#### 3.6.3 实时驾驭与异步消息队列
- **功能描述**: 用户可以在Agent执行任务的任何时刻，通过输入新的指令来实时“驾驭”或“修正”Agent的行为。
- **基本流程**:
  1. 用户的实时输入被放入一个**异步消息队列**。
  2. Agent的核心执行循环在每个关键决策点（如完成一个`Todo`项后）检查此队列。
  3. 如果检测到新指令，Agent将暂停当前计划，优先处理用户的新指令，并可能因此调整其`Todo`清单的后续内容。

### 3.7 个人助理模块

#### 3.7.1 任务理解
**功能描述**：个人助理能够理解用户提出的复杂任务。
**参与者**：用户、个人助理
**前置条件**：系统正常运行。
**后置条件**：任务被正确理解和分解。
**基本流程**：
1. 用户向个人助理提出任务请求。
2. 个人助理分析任务内容。
3. 个人助理识别任务类型和要求。
4. 个人助理分解复杂任务为子任务。
5. 个人助理确认任务理解准确性。

#### 3.7.2 任务执行
**功能描述**：个人助理协调资源执行用户任务。
**参与者**：个人助理、AI角色、系统组件
**前置条件**：任务已被正确理解。
**后置条件**：任务被成功执行并返回结果。
**基本流程**：
1. 个人助理制定任务执行计划。
2. 个人助理分配子任务给相应角色。
3. 个人助理监控任务执行进度。
4. 个人助理协调任务间依赖关系。
5. 个人助理收集任务执行结果。
6. 个人助理整合最终结果。

#### 3.7.3 结果反馈
**功能描述**：个人助理向用户提供任务执行结果。
**参与者**：个人助理、用户
**前置条件**：任务执行完成。
**后置条件**：用户收到清晰的结果反馈。
**基本流程**：
1. 个人助理整理任务执行结果。
2. 个人助理生成结果报告。
3. 个人助理向用户展示结果。
4. 用户查看和评估结果。
5. 用户可以请求进一步解释或修改。

### 3.8 AI驱动的项目脚手架 (新增核心功能)

**功能名称**: AI驱动的“团队与SOP”生成器

**用户故事**: “作为一名用户，我希望能用自然语言描述我的项目目标、我想要的虚拟团队角色构成、以及他们之间的协作流程（SOP），以便系统能够自动为我创建和配置好所有必需的AI角色文件和工作流文件，从而极大地节省我的时间和精力。”

**功能需求规格**:

1.  **输入**: 系统必须提供一个专门的入口来接收用户的自然语言描述。
    *   **CLI**: `daip project scaffold --description "一段详细描述..."` 或 `--from-file "描述文件.txt"`。
    *   **Web UI**: 一个专用的多行文本输入框。

2.  **核心处理流程**:
    *   **LLM分析**: 系统将用户的输入文本，嵌入到一个预设的“元提示词（Meta-Prompt）”中，然后调用当前配置的LLM进行分析。
    *   **内容生成**: LLM的任务是识别角色和SOP，并生成所有需要创建的文件的**文件名**和**完整、有效的YAML内容**。
    *   **校验与自我修正**: 在收到LLM的输出后，系统**必须**在内存中对生成的YAML内容进行严格的语法和逻辑校验。如果校验失败，系统应自动将**错误信息**连同原始请求再次发给LLM，并指令它进行自我修正（最多重试2次）。
    *   **用户预览与确认**: 在所有内容都通过校验后，系统**必须**在界面上向用户清晰地展示它即将创建的所有文件名和文件内容，并提供**“确认创建”**和“取消”的选项。
    *   **文件写入**: 只有在用户确认后，系统才能将这些文件真实地写入本地的`roles/`和`workflows/`目录中。

3.  **生成内容的深度要求**:
    *   **角色文件**: 生成的角色YAML中，除了`name`和`description`，系统必须尝试为该角色生成一个高质量、有针对性的**初始提示词模板**，并一同创建对应的模板文件存入`prompts/`目录。
    *   **工作流文件**: 生成的工作流YAML中，必须清晰地定义任务（tasks）、任务间的依赖关系（dependencies）、以及每个任务与角色的正确关联。

4.  **边界情况处理**:
    *   如果系统分析后认为用户的输入与定义团队和SOP无关，或信息过于模糊无法生成有效配置，它不应强行生成，而是应向用户返回一条说明性的提示。
    *   **失败降级**: 如果LLM在多次自我修正后依然无法生成可通过校验的配置，系统不应只提示“失败”，而应为用户提供一个**降级路径**，例如：“AI无法自动生成配置。我们为您准备了一个包含通用注释的模板，您可以在此基础上进行手动修改。”

### 3.9 内置核心工具集 (新增核心功能)

**功能描述**: 为满足非技术用户的核心工作流，系统必须“开箱即用”，内置一套无需额外开发、通过集成现有库实现的常用文档处理工具。

**核心工具列表**:
1.  **论文下载**: 提供一个工具，可以根据关键词从公开学术网站（如 arXiv）搜索和下载论文。
2.  **文档生成**: 提供一个工具，可以将一系列文本、数据或会话记录，整合成一个格式化的`.docx`或`.pdf`文件。
3.  **格式转换**: 提供一个工具，用于常见的文档格式转换，特别是 `Markdown -> DOCX` 和 `Markdown -> PDF`。

**实现原则**:
- **集成而非重造**: 这些工具应通过集成业界成熟的开源库（如 `python-docx`, `arxiv`）或命令行工具（如 `pandoc`）来实现。
- **默认启用**: 这些工具应作为系统的默认工具集，默认启用并可被分配给合适的AI角色。

## 4. 非功能需求 (单机版)

### 4.1 性能需求

#### 4.1.1 响应速度
- **UI响应**: CLI命令应在100ms内给出即时反馈。Web UI中的操作（点击、输入）应无明显延迟。
- **LLM交互**: 使用本地LLM时，响应时间取决于模型大小和硬件；使用云端LLM时，端到端响应时间应主要取决于模型生成速度和网络延迟。
- **知识检索**: 对本地知识库的语义搜索，应在1秒内返回结果。
- **应用启动**: 应用冷启动时间应在5秒以内。

#### 4.1.2 资源占用
- **内存**: 空闲时内存占用应小于500MB。处理大型任务或加载大型模型时，内存使用应在合理范围内，且无内存泄漏。
- **CPU**: 空闲时CPU占用应接近0%。计算密集型任务（如向量化）期间，应能有效利用多核CPU，并在任务结束后恢复到低占用状态。

### 4.2 可靠性需求

#### 4.2.1 应用稳定性
- 应用在长时间运行（例如连续运行24小时）下应保持稳定，不会意外崩溃。
- 能够优雅地处理错误输入和异常文件格式，而不是直接崩溃。
- 数据库（SQLite）和索引文件（FAISS/ChromaDB）应具备基本的事务性和写安全，避免因意外中断导致数据损坏。

#### 4.2.2 数据完整性
- 所有用户的配置、会话历史和知识库元数据都应被准确、完整地持久化到本地存储中。
- 提供简单的本地备份机制（例如，将数据目录打包成zip文件），并能从中恢复。

#### 4.2.3 外部依赖校验
- **启动时检查**: 应用在启动时，必须主动检查像`pandoc`这样的关键外部依赖是否存在于系统PATH中。
- **优雅降级**: 如果检测到依赖不存在，应用不应崩溃。而应禁用依赖于此功能的特性（如文档转换），并在UI中显示一个全局的、可关闭的警告，引导用户去安装。

### 4.3 可扩展性需求

#### 4.3.1 数据规模扩展
- 系统应能高效地管理和索引不断增长的本地知识库（例如，支持数千份文档，总大小达到GB级别）。
- SQLite数据库应能处理数十万条记录（如消息、会话）而无明显性能下降。

#### 4.3.2 功能扩展
- **模型可扩展**: “模型提供者”模块应采用插件化设计，可以方便地通过添加新的Provider文件来支持新的本地或云端LLM。
- **工具可扩展**: AI角色使用的工具应是可插拔的。用户可以开发自己的Python函数，并将其注册为AI可调用的新工具。

### 4.4 安全性需求

#### 4.4.1 工具使用权限控制
为给予用户对高风险工具（如执行Shell命令、写入文件）的完全控制力，系统必须实现一个精细化的权限控制机制。
- **三元策略 (Allow/Deny/Ask)**: 用户必须可以在`config.yaml`中，为每一个工具或每一类工具设置权限策略：
  - `allow`: 允许AI角色自动执行。
  - `deny`: 完全禁止执行，调用会直接失败。
  - `ask`: **(默认)** 在执行前，必须在UI/TUI中弹框请求用户手动确认。
- **通配符规则**: 对于`bash`等工具，权限策略应支持通配符。例如，用户可以设置：
  - 允许: `git *`, `ls`
  - 禁止: `rm *`, `mv *`
  - 对其他所有命令: `ask`

#### 4.4.2 本地数据安全
- **API密钥安全**: 对于存储的云端服务API密钥，必须进行加密处理，不能明文存储在配置文件中。应优先使用操作系统提供的密钥管理工具（如Windows Credential Manager, macOS Keychain）。
- **文件访问**: 应用应仅访问由用户明确指定的目录（如知识库目录），避免对用户文件系统进行无限制的读写操作。

#### 4.4.3 代码安全
- **依赖安全**: 定期扫描项目依赖库，避免引入存在已知漏洞的第三方包。
- **输入处理**: 对用户输入和从文件中读取的内容进行适当的清理和验证，以防止潜在的命令注入等问题（尽管在单用户环境下风险较低）。

### 4.5 兼容性需求

#### 4.5.1 操作系统兼容性
- 系统应能在主流的桌面操作系统上稳定运行：Windows 10/11, macOS (Apple Silicon & Intel), 主流Linux发行版 (如Ubuntu 20.04+)。

#### 4.5.2 浏览器兼容性 (针对Web UI)
- 本地Web UI应在最新版本的Chrome, Firefox, Safari, Edge浏览器上正常显示和使用。

#### 4.5.3 平台无关性 (核心开发约束)
- **禁止直接调用特定平台的Shell指令**。所有文件和目录操作（如列表、创建、复制、删除）**必须**使用Python的`os`, `shutil`, `pathlib`等跨平台标准库来完成，以确保代码在Windows, macOS, Linux上行为一致。

### 4.6 易用性与交互体验需求

#### 4.6.1 通用易用性
- **首次运行配置向导**: 应用首次运行时，应在Web UI或TUI中启动一个配置向导，引导用户完成最核心的设置（如选择知识库目录、配置LLM提供者）。
- **学习成本**: 新用户通过阅读`README`和用户手册，应在5分钟内可完成基本操作。
- **帮助系统**: CLI的每个命令都应有`--help`说明。UI应内置可搜索的帮助文档或FAQ。
- **可访问性**: 界面应支持基本的辅助功能，如键盘导航和高对比度模式。

#### 4.6.2 “Gemini模式”TUI/UI 交互需求
为提供极致的透明度和协同感，TUI和UI的核心交互界面必须实现以下特性：

1.  **显式的意图与规划 (Thinking Process)**:
    *   在执行任何复杂操作或调用工具前，系统应首先清晰地展示其“思考”或“计划”。例如，显示：“*我将搜索知识库以寻找相关信息，然后调用代码生成工具。*”

2.  **透明的工具调用 (Tool Call Display)**:
    *   当系统使用工具时，必须在界面上以一个独立的、高亮的区块展示完整的工具调用信息，包括工具名称和传入的参数。

3.  **明确的工具输出 (Tool Output Display)**:
    *   工具执行后的返回结果，必须在一个独立的、结构化的区块中展示。
    *   该区块需用颜色（如绿/红）或图标明确标识**成功/失败**状态。
    *   对于代码或JSON等结构化输出，必须进行**语法高亮**。
    *   对于长文本输出，必须支持在区块内**滚动查看**，并告知用户总行数。
    *   对于图片等非文本数据，必须显示其元信息描述。

4.  **流式响应 (Streaming LLM Responses)**:
    *   所有来自LLM的最终文字回答，都必须以**流式“打字机”**的效果逐字显示，以提供即时反馈。

5.  **Markdown渲染 (Markdown Rendering)**:
    *   界面必须能正确解析并渲染LLM回答中的Markdown语法，包括列表、粗体、斜体和带语法高亮的代码块。。

## 5. 约束条件 (单机版)

### 5.1 技术约束
- **后端语言**: Python 3.9+。
- **UI框架**: 
  - **CLI/TUI**: Typer / Textual。
  - **图形界面 (GUI)**: 初期使用Streamlit进行快速原型开发，长期目标为原生GUI框架 (如Tauri, PySide)以提供最佳本地集成体验。
- **数据存储**: 结构化数据使用**SQLite**，向量化知识使用**嵌入式库（FAISS/ChromaDB）**。
- **部署环境**: 在用户的本地Python环境中直接运行，**不使用**Docker或Kubernetes。

### 5.2 数据约束
- **数据位置**: 所有用户数据，包括配置、知识库和会话历史，都存储在用户本地文件系统上。
- **编码标准**: 所有由系统生成或读取的文本文件（如日志、配置文件、知识源），都**必须**默认使用`utf-8`编码，以防止跨平台出现乱码问题。
- **数据备份**: 数据备份由用户自行负责，通过简单地复制数据目录来完成。
- **日志**: 系统日志默认保存7天，用户可配置保留期限。

### 5.3 法规约束
- **数据隐私**: 由于是本地应用，用户数据默认不离开个人电脑。如果使用云端LLM服务，用户需遵守相应服务商的数据使用策略。
- **AI伦理**: 系统生成的任何内容都应被视为AI辅助创作，用户需对最终用途负责。

### 5.4 业务约束
- **离线核心**: 系统的核心功能（使用本地LLM、管理本地知识）必须支持完全离线运行。
- **部署模式**: 系统仅支持此单机版部署模式。
- **接口文档**: 无需提供Web API文档。开发者文档应聚焦于内部模块的函数接口和如何扩展新功能（如模型提供者、工具）。
