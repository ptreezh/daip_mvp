# 系统测试策略和用例说明书 (单机版)

## 1. 概述

本文档为DAIP-LIVE（单机版）定义了全面的测试策略，旨在确保这个模块化单体应用的**功能正确性、本地数据安全性、以及在用户本地环境中的运行稳定性**。

## 2. 测试策略

### 2.1 测试原则
- **本地化优先**: 测试的重点是验证在普通用户电脑上的功能，而非服务器环境。
- **高度自动化**: 核心功能通过自动化的单元和集成测试覆盖，确保代码重构和功能迭代的安全性。
- **用户场景驱动**: 系统级测试由真实的用户使用场景驱动，确保软件的实用性。

### 2.2 测试层次
1.  **单元测试 (Unit Tests)**: 验证单一函数或类的内部逻辑。**目标**: 覆盖核心算法、数据处理和工具函数的各种边界情况。覆盖率目标 > 85%。
2.  **集成测试 (Integration Tests)**: 验证模块之间的直接函数调用和交互是否正确。**目标**: 确保模块组合后能协同工作，特别是与数据库、文件系统的交互。
3.  **系统测试 (System/E2E Tests)**: 通过程序化地调用CLI命令或模拟Web UI操作，验证完整的端到端用户流程。**目标**: 模拟用户真实操作，确保整个应用流程通畅，结果符合预期。

### 2.3 测试环境
- **本地开发环境**: 所有测试均在标准的本地开发环境中执行，与最终用户环境保持一致。测试前会设置一个临时的、独立的测试数据库（如内存中的SQLite或一个测试用的DB文件）和数据目录，确保测试不会污染用户的实际数据，且可重复执行。

## 3. 测试工具和技术

- **测试框架**: **Pytest** (主要) 和 `unittest` (辅助)。
- **模拟与伪造 (Mocking)**: 使用 `unittest.mock` 来隔离测试单元，特别是模拟对LLM的调用，使测试不依赖网络或本地大模型，从而变得快速和确定。
- **CLI测试**: 使用`pytest`结合`Typer`的测试工具，对命令行应用的输入和输出进行断言。
- **UI测试 (可选)**: 可使用 `selenium` 或 `playwright` 对Streamlit生成的Web UI进行自动化冒烟测试。

## 4. 测试用例示例

### 4.1 单元测试 (Unit Tests)

- **测试用例ID**: UT_KM_001
- **模块**: 知识管理器 (Knowledge Management)
- **测试目标**: 验证`chunk_text`函数能否正确地将长文本按句子边界切分成指定大小的块。
- **测试步骤**:
  1.  创建一个包含多句话的长字符串。
  2.  调用`chunk_text`函数，传入该字符串和最大块大小参数。
  3.  断言返回的块列表数量符合预期。
  4.  断言每个块的长度都不超过最大值。
  5.  断言块的切分点都在句子末尾。
- **预期结果**: 函数按预期正确切分文本。

### 4.2 集成测试 (Integration Tests)

- **测试用例ID**: IT_PA_KM_001
- **涉及模块**: 个人助理 (PA) & 知识管理器 (KM)
- **测试目标**: 验证当PA被要求回答问题时，它能否成功调用KM进行知识检索。
- **前置条件**: 
  1.  设置一个临时的SQLite数据库和知识目录。
  2.  在知识目录中放置一个测试文档并运行知识索引流程。
  3.  使用`mock`替换掉`ModelProvider`模块，使其不发生真实的LLM调用。
- **测试步骤**:
  1.  实例化`PersonalAssistant`和`KnowledgeManager`。
  2.  调用PA的`ask(question)`方法，问题与测试文档内容相关。
  3.  断言`KnowledgeManager`的`search_knowledge`方法被成功调用，且传入的参数是正确的查询语句。
- **预期结果**: 模块间调用链正确，参数传递无误。

### 4.3 系统测试 (System Tests)

- **测试用例ID**: ST_CLI_DEBATE_001
- **测试目标**: 验证通过CLI成功发起一场完整的辩论，并检查其在数据库中的记录。
- **前置条件**: 
  1.  设置一个临时的、空的测试数据库文件。
  2.  `config.yaml`已配置好一个被mock的LLM提供者。
- **测试步骤**:
  1.  使用`subprocess`或`Typer`的测试运行器，执行CLI命令 `daip debate start "测试主题" --rounds 2`。
  2.  捕获CLI的输出，断言输出了辩论开始和各轮次的提示信息。
  3.  待命令执行完毕，连接到测试数据库文件。
  4.  查询`sessions`表，断言已创建一条类型为`debate`、主题为“测试主题”的记录。
  5.  查询`messages`表，断言生成了对应2轮辩论的消息记录。
- **预期结果**: CLI命令成功执行，并在数据库中留下了正确的数据记录。

## 5. 验收测试场景

- **场景ID**: AT_LOCAL_LLM_001
- **场景描述**: 用户希望使用本地Ollama运行的Llama3模型，对本地文件夹中的一组Markdown文档进行问答。
- **测试步骤**:
  1.  **安装与配置**: 按照用户手册，完成应用的安装，并在`config.yaml`中将`model_provider`设置为`ollama`，模型名称设置为`llama3`。
  2.  **知识库建立**: 通过CLI或Web UI，将本地Markdown文档所在的文件夹指定为知识库路径，并执行索引命令。
  3.  **问答交互**: 启动Web UI，新建一个聊天会话，提出一个与文档内容相关的问题。
- **验收标准**:
  - 系统能够正确索引所有文档，UI上能看到索引状态。
  - 提问后，AI的回答内容与文档内容高度相关，表明知识检索和上下文注入成功。
  - 整个过程无需访问互联网（可断网测试）。


## 6. 测试覆盖要求

- **共识验证**: 需验证辩论系统生成的共识结果是否符合逻辑一致性。
  - 新增模糊测试策略：通过随机输入变异生成对抗性测试用例（如矛盾前提、极端边界条件）
  - 集成偏见检测验证：自动检查共识报告中是否包含偏见风险标注
  - 实现工作流超时熔断测试：验证子Agent在300秒阈值后自动终止并恢复机制
