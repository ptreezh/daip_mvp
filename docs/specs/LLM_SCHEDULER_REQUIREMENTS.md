# LLM模型提供者需求文档

## 1. 功能概述

**LLM模型提供者 (Model Provider)** 是DAIP-LIVE（单机版）的核心驱动模块。它并非一个“调度器”，而是一个**抽象层**，其主要职责是封装与不同类型的大语言模型（本地模型、云端API）的交互细节，为上层应用提供一个统一、简洁的调用接口。

## 2. 核心功能

### 2.1 提供者抽象与管理
- **统一接口**: 必须定义一个所有模型提供者都要遵循的标准化接口，至少包含 `generate(prompt, params)` 和 `embed(text)` 两个核心函数。
- **动态加载**: 系统应能根据主配置文件 (`config.yaml`) 中指定的 `default_provider`，在启动时动态加载并实例化对应的提供者类。
- **可插拔架构**: 添加对新模型或新服务的支持应是简单、低耦合的。理想情况下，只需在 `providers/` 目录下新增一个遵循接口规范的Python文件即可，无需修改核心代码。

### 2.2 本地模型支持
- **Ollama集成**: 必须内置一个与本地Ollama服务交互的提供者，能调用Ollama中已有的任何模型。
- **GGUF/llama.cpp集成 (可选)**: 可考虑提供一个能通过`llama-cpp-python`库直接加载`.gguf`模型文件的提供者，以摆脱对Ollama服务的依赖，实现纯应用内运行。

### 2.3 云端模型支持
- **主流API集成**: 必须内置对主流云端LLM服务的支持，至少包括OpenAI、Google Gemini、Anthropic Claude等。
- **API密钥管理**: 提供者必须能安全地从配置或环境变量中获取API密钥，并在请求时使用。
- **错误处理**: 必须能优雅地处理API相关的错误，如认证失败、速率限制、无效请求等，并返回清晰的错误信息给上层应用。

### 2.4 上下文管理
- **长上下文优化**: 必须提供处理长上下文的策略，例如使用滑动窗口或在调用LLM前对过长的上下文进行摘要。
- **Token计算**: 提供一个工具函数，用于准确计算给定文本的token数量，以避免超出模型上下文窗口限制。

### 2.5 工具调用支持
- **Function Calling/Tool Use**: 必须支持现代LLM的工具调用能力。提供者应能将上层应用定义的工具（Python函数）格式化成模型需要的格式，并能解析模型返回的工具调用请求。

## 3. 非功能需求

### 3.1 易配置性
- 用户应能通过简单地修改`config.yaml`文件，轻松切换全局使用的LLM，或为特定角色指定不同的LLM。

### 3.2 稳定性与容错性
- **服务可用性**: 当配置的LLM服务（本地或云端）不可用时，系统不能崩溃，而应向上层返回明确的、用户可理解的错误信息（例如，“无法连接到Ollama服务，请确认其是否正在运行”）。
- **API错误处理**: 提供者应包含合理的超时和重试机制（尤其对于云端API调用）。
- **资源预检 (Resource Pre-checking)**: 对于需要直接加载模型到内存的本地提供者（如`llama.cpp`），在加载模型前，**必须先检查当前系统的可用内存/显存**。如果预估的模型加载所需资源超过系统可用资源，应拒绝加载并向用户返回明确的警告信息，而不是直接尝试加载导致程序崩溃。

### 3.3 可扩展性
- 架构必须清晰，文档必须完备，以鼓励社区或用户自己贡献新的模型提供者。
