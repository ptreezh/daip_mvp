# 角色管理需求文档 (单机版)

## 1. 功能概述

角色管理模块负责DAIP-LIVE（单机版）中AI角色的定义、加载和配置。它是决定AI行为方式的核心组件，所有操作均在本地完成。它与提示词管理和工具调用机制紧密耦合。

## 2. 核心功能

### 2.1 角色定义
- **基于文件的定义**: 角色应通过结构化的本地文件（推荐使用**YAML**）进行定义，便于用户阅读和修改。
- **本地目录加载**: 系统应能自动从指定的本地文件夹（如 `roles/`）发现并加载所有角色定义文件。
- **核心属性**: 角色定义必须包含 `name`, `description`, `prompt_template_file` (指向提示词模板文件), 和 `tools` (可使用的工具列表)。

### 2.2 提示词管理 (Prompt Management)
- **中央目录**: **所有的提示词模板都必须存放在项目根目录下的 `prompts/` 文件夹中**。这使得用户可以方便地在一个地方查看、修改和管理所有AI行为的底层指令。
- **模板引用**: 角色配置文件中不直接包含冗长的Prompt，而是通过`prompt_template_file`字段，引用`prompts/`目录下的一个模板文件。
- **指引文件**: `prompts/`目录下必须包含一个`README.md`文件，详细解释每个模板文件的用途、支持的变量以及如何进行有效的修改。
- **模板引擎**: Prompt模板应支持使用专业的模板引擎（如 **Jinja2**），以实现更复杂的逻辑。

### 2.3 角色能力：工具与模型

#### 2.3.1 工具调用与执行管道 (Tool Use & Execution Pipeline)
为确保工具调用的健壮与安全，每一次工具调用都必须经过以下管道流程：

1.  **工具发现 (Discovery)**: 系统根据LLM生成的工具名称，在中央“工具注册表”中查找对应的已注册Python函数。
2.  **输入验证 (Input Validation)**: **(关键步骤)** 所有工具函数的参数必须使用**Pydantic**模型进行定义。在执行函数前，系统必须用此模型验证LLM生成的参数。**验证失败则拒绝执行**，并可将错误信息返回给LLM，令其自我修正。
3.  **安全前置条件校验 (Security Precondition Check)**: 
    *   **“写前必须读”原则**: 对于所有文件写入或修改类工具（如 `write_file`, `replace`），系统**必须**检查该文件是否在近期的对话历史中被`read_file`工具读取过。如果否，则拒绝执行，并强制AI必须先读取文件以了解最新内容。
4.  **权限检查 (Permission Check)**: 系统根据`config.yaml`中为该工具设定的`allow/deny/ask`策略，决定是直接执行、拒绝执行、还是在UI/TUI中弹框**询问用户**以获得授权。
5.  **执行与监控 (Execution & Monitoring)**: 执行工具函数。执行过程应支持**超时控制**和**用户中断**信号。
6.  **结果格式化 (Result Formatting)**: 将工具函数的返回值（或异常信息）包装成一个标准化的、可被LLM理解的格式，再送回给AI进行下一步思考。

#### 2.3.2 工具定义与注册
- **工具即函数**: 系统中的“工具”被定义为具体的Python函数。
- **自动注册**: 任何Python函数只要使用了特定的装饰器（`@tool`），就应能被自动注册到“工具注册表”中。装饰器负责提取函数名、描述(docstring)和基于Pydantic的参数Schema。
- **角色声明**: 每个角色的定义文件必须明确声明一个`tools`列表，指明该角色被授权使用哪些已注册的工具。
- **跨平台开发准则 (核心)**: 所有工具的开发者**必须**保证其代码的平台无关性。进行文件路径操作时，**必须**使用`pathlib`库；进行文件读写、复制等操作时，**必须**使用`shutil`等标准库。**严禁**在工具代码中硬编码`ls`, `cp`, `mkdir`等特定于Linux/macOS或Windows的Shell命令。

#### 2.3.3 模型绑定 (可选)
- 允许为特定角色绑定一个不同于全局配置的LLM提供者。

### 2.4 角色生命周期与应用
- **内存加载**: 应用启动时，将角色定义文件解析并加载到内存中。
- **会话应用**: 支持用户在单个会话中选用一个或多个AI角色参与交互。
- **任务分配**: 在工作流中，可以将不同的任务节点分配给具有不同能力的特定角色来执行。

## 3. 非功能需求

- **灵活性**: 用户通过修改YAML文件就能增删和配置角色。
- **性能**: 快速加载角色配置，每个角色对象内存占用低。
- **可管理性**: 对角色、提示词、工具的加载失败提供清晰的错误日志，并在UI中提供浏览界面。

## 4. 配置 (Configuration)

角色管理模块的配置在 `config.yaml` 文件中定义，具体如下：

```yaml
role_manager:
  roles_dir: "roles/"
```

- `roles_dir`: 指定包含角色定义（YAML文件）的目录路径。

`AppConfig` 模型中也应包含相应的 `RoleManagerConfig` 模型来验证此配置。
