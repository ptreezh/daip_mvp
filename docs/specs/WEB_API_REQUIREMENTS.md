# 接口需求说明 (单机版)

## 1. 核心原则变更

根据DAIP-LIVE（单机版）的**单机、单用户**核心定位，原有的、面向多用户的、基于HTTP的RESTful Web API需求被**废弃**。系统的主要交互方式是**命令行界面 (CLI)** 和一个与后端逻辑直接集成的**本地图形界面 (Web UI)**。

## 2. 交互接口定义

### 2.1 命令行接口 (CLI)
- **定位**: 主要接口，用于脚本化、自动化和高级操作。
- **实现**: 通过Python的Typer或Click库实现，提供丰富的子命令和参数。
- **交互**: 用户在终端中直接执行命令，应用同步返回结果。

### 2.2 本地图形界面 (Local Web UI)
- **定位**: 为用户提供直观、易用的图形化操作环境。
- **实现**: 基于Streamlit框架。Streamlit的特性决定了UI可以直接调用后端的Python函数来获取数据和执行操作，**无需通过HTTP API进行通信**。
- **交互**: 用户在浏览器中访问本地服务地址（如`http://localhost:8501`），所有操作的响应都在同一个Python进程内完成，具有极高的效率。

### 2.3 内部接口 (Internal APIs / Function Calls)
- **定位**: 应用内部各模块之间的通信方式。
- **实现**: **纯粹的Python函数调用**。例如，`web_ui`模块直接调用`core_logic`模块提供的函数。
- **优点**: 零网络开销，高性能，强类型检查（如果使用类型提示），易于调试和重构。

## 3. 实时通信需求

- **需求**: 在Web UI中，当一个长时间运行的任务（如辩论或工作流）在后台执行时，需要将状态和结果实时更新到前端页面。
- **实现**: 
  - **方案A (推荐)**: 利用Streamlit的内建机制。可以通过定期刷新页面、或者将会话状态（Session State）与后台任务状态关联来实现伪实时更新。
  - **方案B (备选)**: 如果需要更精细的实时推送，可以保留一个极简的、本地的WebSocket服务。此服务仅用于从后端任务向前端UI推送状态更新，不承载复杂的业务逻辑，且无需复杂认证。

## 4. 第三方集成 (可选)

如果未来有需求允许外部应用与DAIP-LIVE交互，可以考虑提供一个极简的、本地的RPC（远程过程调用）或HTTP API，但它必须遵循以下原则：
- **默认禁用**: 需要用户在配置文件中显式启用。
- **本地绑定**: 仅监听`127.0.0.1`，不暴露于局域网。
- **无需认证**: 因为是本地单用户环境，可以免除复杂的用户认证流程。

**结论**: 在当前的单机架构下，一个复杂的、类似`API_INTERFACE_SPECIFICATION.md`中定义的Web API已无必要，相关开发和维护工作应被取消。
